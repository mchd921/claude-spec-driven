# 要件定義書: 筋トレ管理アプリ (Workout Tracker)

- ステータス: 承認済み（2026-11-17）
- 作成日: 2026-11-16
- 更新日: 2026-11-17（受け入れ基準を厳密な EARS 形式に書き直し / 未決事項を反映）

## 1. 概要

個人が筋力トレーニングの内容を記録し、成長を振り返るための Web アプリケーション。
データはブラウザ内（ローカル）に保存し、サーバーやログインなしで利用できる。

### 1.1 想定ユーザー

- ジムや自宅で筋トレを行う個人（1 ユーザー・1 端末を想定）
- 主にスマートフォンのブラウザでトレーニング中に記録し、PC でも閲覧する

### 1.2 スコープ

| 対象 (MVP) | 対象外 (将来検討) |
| --- | --- |
| トレーニング記録 | ユーザー登録・ログイン |
| 種目マスタ管理 | 複数端末間の同期・クラウド保存 |
| 履歴・グラフ表示 | SNS 共有 |
| メニュー（テンプレート） | 有酸素運動の詳細記録（距離・心拍など） |
| データのエクスポート / インポート | 体重・体脂肪などの身体記録 |
| | インターバルタイマー |
| | 重量単位 lb（kg のみ対応） |

## 2. 用語定義

| 用語 | 定義 |
| --- | --- |
| 種目 (Exercise) | ベンチプレス、スクワットなどのトレーニング種類 |
| 部位 (Body Part) | 胸・背中・脚・肩・腕・腹・その他 のいずれか |
| セット (Set) | 1 種目を 1 回連続して行った単位。重量と回数を持つ |
| ワークアウト (Workout) | 1 回のトレーニングセッション。日付・メモと、複数種目・複数セットを含む。同じ日付に複数存在してよい |
| 進行中 / 完了 | ワークアウトの状態。開始時は「進行中」、終了操作で「完了」になる |
| メニュー (Template) | 種目の順序付きリストに名前を付けて保存したもの |
| ボリューム | 対象セットの「重量 × 回数」の合計 |
| 推定 1RM | Epley 式 `重量 × (1 + 回数 / 30)` で算出する最大挙上重量の推定値 |
| 自己ベスト (PR) | ある種目について、そのセット以前の全セットの値を上回った最大重量または推定 1RM |
| 有効な種目 | アーカイブされていない種目 |
| 有効なセット値 | 重量 (kg) が 0〜999.9 の 0.1 刻みの数値、かつ回数が 1〜999 の整数であるもの。自重種目は重量 0 として記録する |

## 3. 機能要件

### 3.1 記法

受け入れ基準は EARS (Easy Approach to Requirements Syntax) で記述する。
各基準の主語は「システム」とし、1 つの基準には 1 つの振る舞いのみを書く。
基準の末尾に使用したパターンを記す。

| 記号 | パターン | 型 |
| --- | --- | --- |
| [常時] | Ubiquitous | システムは〜しなければならない |
| [イベント] | Event-driven | 〜とき、システムは〜しなければならない |
| [状態] | State-driven | 〜の間、システムは〜しなければならない |
| [異常] | Unwanted behavior | もし〜ならば、システムは〜しなければならない |
| [オプション] | Optional feature | 〜場合、システムは〜しなければならない |

基準 ID（例: `REQ-1.3`）は設計書・タスク・テストから参照する。

### 要件 1: トレーニング記録

**ユーザーストーリー:** ユーザーとして、トレーニング中にその場で種目・重量・回数を素早く記録したい。後で振り返るためである。

**受け入れ基準:**

| ID | 基準 |
| --- | --- |
| REQ-1.1 | ユーザーが「ワークアウト開始」を選択したとき、システムは日付を当日、状態を進行中とする空のワークアウトを作成しなければならない。[イベント] |
| REQ-1.2 | ユーザーが種目追加を選択したとき、システムは有効な種目の一覧を部位ごとに分類して表示しなければならない。[イベント] |
| REQ-1.3 | ユーザーが種目一覧で部位を選択したとき、システムは選択した部位の有効な種目のみを表示しなければならない。[イベント] |
| REQ-1.4 | ユーザーが種目一覧から種目を選択したとき、システムはその種目を表示中のワークアウトの末尾に追加しなければならない。[イベント] |
| REQ-1.5 | 追加した種目に過去のワークアウトでの記録がある場合、システムは直近のワークアウトでのその種目の全セットを参考として表示しなければならない。[オプション] |
| REQ-1.6 | ワークアウト内のその種目に記録済みのセットがある場合、システムはセット入力欄の初期値に、その種目の最後のセットの重量と回数を設定しなければならない。[オプション] |
| REQ-1.7 | ワークアウト内のその種目に記録済みのセットがなく、過去の記録がある場合、システムはセット入力欄の初期値に、直近のワークアウトでのその種目の最初のセットの重量と回数を設定しなければならない。[オプション] |
| REQ-1.8 | ユーザーが有効なセット値でセット追加を確定したとき、システムはそのセットを種目の末尾に追加しなければならない。[イベント] |
| REQ-1.9 | もしセット追加の確定時に入力値が有効なセット値でないならば、システムはセットを追加せず、不正な入力欄の近くにエラー内容を表示しなければならない。[異常] |
| REQ-1.10 | ユーザーが記録済みのセットを有効なセット値で編集して確定したとき、システムはそのセットの重量と回数を更新しなければならない。[イベント] |
| REQ-1.11 | もしセット編集の確定時に入力値が有効なセット値でないならば、システムはセットを更新せず、不正な入力欄の近くにエラー内容を表示しなければならない。[異常] |
| REQ-1.12 | ユーザーがセットの削除を選択したとき、システムはそのセットをワークアウトから削除しなければならない。[イベント] |
| REQ-1.13 | ユーザーがワークアウト内の種目の削除を選択したとき、システムはその種目とその種目の全セットをワークアウトから削除しなければならない。[イベント] |
| REQ-1.14 | ユーザーがメモを入力したとき、システムはそのメモをワークアウトに保存しなければならない。[イベント] |
| REQ-1.15 | もし入力されたメモが 500 文字を超えるならば、システムは 501 文字目以降の入力を受け付けてはならない。[異常] |
| REQ-1.16 | ユーザーがワークアウトの日付を当日以前の日付に変更したとき、システムはワークアウトの日付を更新しなければならない。[イベント] |
| REQ-1.17 | もし変更後の日付が翌日以降ならば、システムは日付を更新せず、エラー内容を表示しなければならない。[異常] |
| REQ-1.18 | セット・種目・メモ・日付のいずれかが変更されたとき、システムはユーザーの保存操作を待たずに変更内容をローカルストレージに保存しなければならない。[イベント] |
| REQ-1.19 | もしローカルストレージへの保存に失敗したならば、システムは保存に失敗した旨を画面に表示しなければならない。[異常] |
| REQ-1.20 | ユーザーが「ワークアウト終了」を選択したとき、システムはそのワークアウトの状態を完了にしなければならない。[イベント] |
| REQ-1.21 | もし終了しようとしたワークアウトにセットが 1 つもないならば、システムはワークアウトを破棄するかどうかの確認を求めなければならない。[異常] |
| REQ-1.22 | ユーザーがセットのないワークアウトの破棄を確定したとき、システムはそのワークアウトを削除しなければならない。[イベント] |
| REQ-1.23 | 進行中のワークアウトがある間、システムはアプリ起動時にそのワークアウトの記録画面を表示しなければならない。[状態] |
| REQ-1.24 | もし進行中のワークアウトがある状態でユーザーが「ワークアウト開始」を選択したならば、システムは新しいワークアウトを作成せず、進行中のワークアウトの記録画面を表示しなければならない。[異常] |
| REQ-1.25 | ワークアウトが完了している間、システムはそのワークアウトのセット・種目・メモ・日付を履歴画面から編集可能にしなければならない。[状態] |

### 要件 2: 種目マスタ管理

**ユーザーストーリー:** ユーザーとして、自分が行う種目を登録・整理したい。記録時に素早く選べるようにするためである。

**受け入れ基準:**

| ID | 基準 |
| --- | --- |
| REQ-2.1 | アプリが初めて起動されたとき、システムは各部位につき 3 種目以上の初期種目を登録しなければならない。[イベント] |
| REQ-2.2 | ユーザーが種目名と部位を入力して種目の追加を確定したとき、システムはその種目を登録しなければならない。[イベント] |
| REQ-2.3 | もし種目名が 1〜50 文字の範囲外ならば、システムは種目を登録せず、エラー内容を表示しなければならない。[異常] |
| REQ-2.4 | もし同じ種目名（前後の空白を除き、大文字・小文字を区別しない）の種目が既に存在するならば、システムは種目を登録せず、重複している旨を表示しなければならない。[異常] |
| REQ-2.5 | ユーザーが種目の名前または部位を編集して確定したとき、システムは種目を更新しなければならない。[イベント] |
| REQ-2.6 | もし編集後の種目名が REQ-2.3 または REQ-2.4 の条件に該当するならば、システムは種目を更新せず、エラー内容を表示しなければならない。[異常] |
| REQ-2.7 | ユーザーがいずれのワークアウト・メニューでも使用されていない種目の削除を確定したとき、システムはその種目を削除しなければならない。[イベント] |
| REQ-2.8 | ユーザーがワークアウトまたはメニューで使用されている種目の削除を確定したとき、システムはその種目を削除せずにアーカイブしなければならない。[イベント] |
| REQ-2.9 | 種目がアーカイブされている間、システムはその種目を種目追加の選択肢に表示してはならない。[状態] |
| REQ-2.10 | 種目がアーカイブされている間、システムはその種目を含む過去のワークアウトを種目名付きで表示しなければならない。[状態] |
| REQ-2.11 | ユーザーがアーカイブ済み種目の復元を選択したとき、システムはその種目を有効な種目に戻さなければならない。[イベント] |

### 要件 3: 履歴・グラフ表示

**ユーザーストーリー:** ユーザーとして、過去のトレーニングと成長の推移を確認したい。モチベーション維持と負荷調整のためである。

**受け入れ基準:**

| ID | 基準 |
| --- | --- |
| REQ-3.1 | ユーザーが履歴画面を開いたとき、システムはワークアウトの一覧を日付の新しい順（同じ日付の場合は作成日時の新しい順）に表示しなければならない。[イベント] |
| REQ-3.2 | システムは履歴一覧の各ワークアウトに、日付・実施種目名・総セット数・総ボリュームを表示しなければならない。[常時] |
| REQ-3.3 | ユーザーが履歴一覧のワークアウトを選択したとき、システムはそのワークアウトの全種目・全セット・メモを表示しなければならない。[イベント] |
| REQ-3.4 | ユーザーがワークアウトの削除を選択したとき、システムは削除の確認を求めなければならない。[イベント] |
| REQ-3.5 | ユーザーがワークアウトの削除を確定したとき、システムはそのワークアウトと含まれる全セットを削除しなければならない。[イベント] |
| REQ-3.6 | ユーザーがカレンダー表示を選択したとき、システムは表示月のうちワークアウトがある日を区別できる形で表示しなければならない。[イベント] |
| REQ-3.7 | ユーザーがカレンダーでワークアウトがある日を選択したとき、システムはその日の全ワークアウトを一覧で表示しなければならない。[イベント] |
| REQ-3.8 | ユーザーがグラフ画面で種目を選択したとき、システムはその種目のワークアウトごとの最大重量の推移を折れ線グラフで表示しなければならない。[イベント] |
| REQ-3.9 | ユーザーがグラフ画面で種目を選択したとき、システムはその種目のワークアウトごとの推定 1RM の最大値の推移を折れ線グラフで表示しなければならない。[イベント] |
| REQ-3.10 | ユーザーがグラフ画面で種目を選択したとき、システムはその種目のワークアウトごとのボリュームの推移を折れ線グラフで表示しなければならない。[イベント] |
| REQ-3.11 | ユーザーがグラフの期間を「1 か月 / 3 か月 / 1 年 / 全期間」から選択したとき、システムは当日から遡って選択した期間内のデータのみをグラフに表示しなければならない。[イベント] |
| REQ-3.12 | もし選択した種目に選択した期間内の記録がないならば、システムは空のグラフではなく「記録がありません」と表示しなければならない。[異常] |
| REQ-3.13 | 記録済みのセットが自己ベスト (PR) に該当する場合、システムはそのセットに PR の印を表示しなければならない。[オプション] |
| REQ-3.14 | セットが追加・編集・削除されたとき、システムは影響する全セットの PR 判定を再計算しなければならない。[イベント] |

### 要件 4: メニュー（テンプレート）

**ユーザーストーリー:** ユーザーとして、いつも行う種目の組み合わせを保存しておきたい。毎回種目を選び直す手間を省くためである。

**受け入れ基準:**

| ID | 基準 |
| --- | --- |
| REQ-4.1 | ユーザーがメニュー名と 1 つ以上の種目を指定してメニューの作成を確定したとき、システムは指定した種目の順序を保ってメニューを登録しなければならない。[イベント] |
| REQ-4.2 | もしメニュー名が 1〜50 文字の範囲外ならば、システムはメニューを登録せず、エラー内容を表示しなければならない。[異常] |
| REQ-4.3 | もしメニューに種目が 1 つも含まれていないならば、システムはメニューを登録せず、エラー内容を表示しなければならない。[異常] |
| REQ-4.4 | メニューの種目に目標セット数（1〜20 の整数）が指定された場合、システムはその目標セット数をメニューに保存しなければならない。[オプション] |
| REQ-4.5 | ユーザーがメニュー内の種目の並べ替えを確定したとき、システムは新しい順序でメニューを更新しなければならない。[イベント] |
| REQ-4.6 | ユーザーがメニューの名前・種目・目標セット数の編集を確定したとき、システムはメニューを更新しなければならない。[イベント] |
| REQ-4.7 | ユーザーがメニューの削除を確定したとき、システムはそのメニューを削除しなければならない。[イベント] |
| REQ-4.8 | ユーザーがメニューを選択してワークアウトを開始したとき、システムはメニューの有効な種目をメニューの順序でワークアウトに追加しなければならない。[イベント] |
| REQ-4.9 | もし開始するメニューにアーカイブ済みの種目が含まれるならば、システムはその種目をワークアウトに追加せず、追加しなかった種目名を表示しなければならない。[異常] |
| REQ-4.10 | メニューから開始したワークアウトの種目に目標セット数がある場合、システムはその種目の記録済みセット数と目標セット数を並べて表示しなければならない。[オプション] |
| REQ-4.11 | ユーザーが記録済みのワークアウトからメニュー作成を選択したとき、システムはそのワークアウトの種目の順序と各種目のセット数を目標セット数として設定したメニュー作成画面を表示しなければならない。[イベント] |

### 要件 5: データ管理

**ユーザーストーリー:** ユーザーとして、記録データを失わないようバックアップしたい。ブラウザのデータ消去や端末変更に備えるためである。

**受け入れ基準:**

| ID | 基準 |
| --- | --- |
| REQ-5.1 | ユーザーが JSON エクスポートを選択したとき、システムは全ての種目・ワークアウト・セット・メニューを含む JSON ファイルをダウンロードさせなければならない。[イベント] |
| REQ-5.2 | システムはエクスポートする JSON ファイルにデータ形式のバージョン番号を含めなければならない。[常時] |
| REQ-5.3 | ユーザーが JSON ファイルのインポートを選択したとき、システムは既存データが置き換えられる旨の確認を求めなければならない。[イベント] |
| REQ-5.4 | ユーザーが妥当な JSON ファイルのインポートを確定したとき、システムは既存の全データをファイルの内容で置き換えなければならない。[イベント] |
| REQ-5.5 | もしインポートするファイルが JSON として読み込めない、または定義済みのデータ形式に適合しないならば、システムは既存データを変更せず、エラー内容を表示しなければならない。[異常] |
| REQ-5.6 | もしインポート処理の途中でエラーが発生したならば、システムは既存データをインポート開始前の状態に保たなければならない。[異常] |
| REQ-5.7 | ユーザーが CSV エクスポートを選択したとき、システムは全セットを「日付, 種目, 部位, セット番号, 重量, 回数」の列で 1 行 1 セットとする CSV ファイルをダウンロードさせなければならない。[イベント] |

## 4. 非機能要件

| ID | 分類 | 基準 |
| --- | --- | --- |
| NFR-1 | 動作環境 | システムは最新版の Chrome / Safari / Firefox / Edge（モバイル版を含む）で全機能が動作しなければならない。[常時] |
| NFR-2 | レスポンシブ | 画面幅が 360px 以上の間、システムは横スクロールなしで全画面を操作可能に表示しなければならない。[状態] |
| NFR-3 | 操作性 | システムは主要な操作ボタンのタップ領域を 44×44px 以上にしなければならない。[常時] |
| NFR-4 | 操作性 | セット入力欄に初期値が設定されている場合、システムは 1 回のタップでセットの追加を確定できなければならない。[オプション] |
| NFR-5 | 性能 | 500 件のワークアウトと 15,000 件のセットが保存されている間、システムは各画面を操作開始から 1 秒以内に表示しなければならない。[状態] |
| NFR-6 | オフライン | 初回読み込みが完了した後、ネットワークに接続されていない間も、システムは全機能を利用可能にしなければならない。[状態] |
